# 项目分析与实现任务反复读取的问题

## 结论

这次失败的主要原因是 Harness 在每次模型请求前主动丢弃了刚读过的源码，
然后在固定迭代上限处强制收尾。只改 System Prompt 或提高迭代次数，无法消除
“读文件 → 正文丢失 → 再读文件”的循环。缺少执行命令阻断了测试验证，但并不
妨碍已有 `edit_file` 修改代码。

## 从用户提供的最后一次请求确认的事实

- 原始用户任务“给我实现 p0 的 1、2、3”仍在上下文里，上轮 P0 定义也保留了。
  这次不是完全丢失用户目标。
- 较早的工具结果被放进 `[Earlier accepted tool activity]`，大多数只剩文件头，
  包含 `原始约 … tokens` 和 `truncated` 标记。
- 最新两次 20 行读取仍是完整 `role=tool` 消息；此前的较大读取却只剩摘录。
- 最后出现合成 user 消息“本轮工具调用预算已经用完”，并且工具定义为无。
  这是 Runner 的收尾请求，不是启动时漏注册了全部工具。

## 对应代码中的原因

1. `ContextGovernor.prepare_request()` 无条件调用
   `_compact_accepted_turn_region()`，把 Provider 已接受过的本轮中间消息换成摘要。
   API 接受请求不提供模型端永久记忆，后续请求必须再次携带需要的源码。
2. `_build_accepted_activity_summary()` 每条工具结果只保留约 80 token，通常只够
   模块注释和 import；整个摘要又只取前 4096 token，后面的发现和修改记录会丢失。
3. `_apply_pressure()` 在小窗口下还会施加固定的单条结果上限，即使总请求放得下。
4. `read_file` 默认返回 2000 行，与默认 8K 上下文的工具 Schema、系统提示词和
   历史竞争空间。没有重复读取提醒或剩余迭代提示。
5. 默认 System Prompt 把“项目分析”直接绑定到 `write_file` 保存报告，并以
   避免虚报为主，没有明确推动“定位 → 编辑 → 验证”。
6. `max_iterations=32` 限制的是正常模型请求轮数，一轮可含多个工具调用。
   达到上限后会额外发起一次 `tools=None` 的总结请求，解释了最后一条提示词。

## 修复后的行为

- 请求放得下时保留工具正文，不根据 accepted 边界或固定单条上限提前裁掉源码。
- 请求超预算时才压缩更早的已接受工具组；最近两组已接受调用和最新调用仍保留
  工具协议结构。旧摘录保留头尾，整体摘要也保留尾部。持续超预算时仍需截断，
  不承诺有限窗口能保留无限源码。
- 原始 Runner/Session 消息不被修改，`accepted_summarized_messages` 只统计实际
  被替换的记录。
- 连续六次只读、同参数成功读取两次、接近迭代上限时加入临时进度提醒。
  不硬禁重读，非只读工具后清空重复统计；提示不写入 Session。
- `read_file` 默认 200 行；提示模型用 `grep` 定位和按相关范围读取。
- 分析任务直接回答，只有用户要求落盘才创建报告。实现任务明确要求尽快编辑
  并验证，缺少验证工具不能被当作无法编辑的理由。
- `run_command` 连接编辑后的测试闭环；`file_info` 用于文件大小、行数和二进制
  检测；`write_file(mode="append")` 避免为追加少量内容重传整个文件。
- Registry 统一提供可取消异步超时和输出限制；命令工具自身限制时间、输出，
  并在 POSIX 上清理进程组。危险命令确认由宿主回调执行。
- 顺便修复 `grep` 遍历到文件符号链接时没有重新验证 Workspace 边界的问题。

## 第二轮：8K 回退值与不可回收摘要

用户清空历史后再次分析项目，仍遇到 `7282 > 7168`。从真实 Session 只读回放中
精确复现了该数值；约 4132 token 来自 `accepted_summary`。工具结果虽已截断，
本地生成的摘要却在普通截断和最终确定性回退中都不可回收，导致仅超出 114 token
也只能终止请求。现在这类摘要同样按实际剩余预算缩小，原始历史仍保持不变。

真实保存配置使用 `deepseek-v4.1-flash-1017`，但 `context_window_tokens=0`、
`max_output_tokens=0`，因此一直回退至 8192 总窗口/1024 预留；实际输出能力
沿用 4096，未指定最高推理档位。此前 CLI 能力选项只在新建配置时传入，复用
保存配置时也会丢失。现已修复覆盖顺序与连接后的立即同步，`/context` 无需
先发送用户消息才显示正确窗口；切换到未知模型也不会继承前一个模型的窗口。

模型/端点资料（2026-11-04 核对）：

- [当前网关模型页面](https://www.qianwenai.com/models/deepseek-v4.1-flash-1017)：
  1M 上下文、384K 最大输出。
- [网关参数文档](https://platform.qianwenai.com/docs/api-reference/chat/openai-chat)：
  此模型支持 `enable_thinking=true` 和 `reasoning_effort="max"`。
- [DeepSeek 原生参数](https://api-docs.deepseek.com/api/create-chat-completion/)：
  输出额度上限 393216，输入与输出总和受上下文窗口约束。

输出能力上限与最低输出预留现已区分：配置 1048576 总窗口与 393216 输出上限
时，默认最低预留 4096，输入预算 1044480；实际输出按剩余空间动态收缩，不会
始终预扣 393216。上下文是总额度，无法让输入、输出各自同时独占全部窗口。

此外，日志里的十次 `run_command` 主要是 `cat`、`sed -n`、`wc`、`grep` 读取。
此前任何 shell 调用都会清空连续只读统计，恰好绕过进度提醒。现在保守识别
常见只读 shell 形式，使它们也计入探索进度；这项识别不用于权限或安全判定。
过时的工具缺口报告也已更新，避免模型把“尚缺 run_command”的旧结论当成现状。

### 本轮验证结果

- 200 项自动化测试通过，新增模型配置覆盖、独立预算覆盖、旧摘要可回收、输出
  额度恢复、不同端点的思考参数格式和只读 shell 识别回归。
- 原始失败 Session 在 8K 配置下只读回放：`7282 > 7168` 已变为
  `7160 <= 7168`；Session 文件字节保持不变。
- 当前默认配置已保存为 1048576 总窗口、393216 最大输出、显式开启思考、
  `reasoning_effort=max`。安装的 `mini-bot` 进程载入后有效输入预算为 1044480。
- 使用当前默认配置与实际网关，通过 AgentRunner 对当前完整项目重新执行
  “分析现有工具及必要缺口”：9 次模型请求、16 次实际工具调用，最大估算输入
  18224 token，`stop_reason=completed`，返回最终分析并包含推理字段。
  此检查不写入用户 Session；另一次工具子系统样例烟测也完成。

这些结果验证了配置发送、较长上下文和工具循环的实际可用性，没有发送 1M
输入做极限负载测试，也不把配置为最高档等同于模型在所有任务上的质量保证。
